1. Foundations in Plain English: How Web Platforms Work

Who This Chapter Is For
If you have never written a line of code or built a website, this chapter is for you. We explain all technical terms (like "frontend", "backend", "database", "API", and "JWT") using simple real-world analogies so you can easily understand how the Tinat platform functions from top to bottom.

1.1 The Real-World Mission: What is Tinat?

Tinat (derived from the Ge'ez / Amharic root ጥናት, meaning "Rigorous Scientific Study" or "In-depth Research") is a complete digital operating system built for medical, public health, and academic research in Ethiopia.

Historically, conducting a research study in Ethiopia (such as an epidemiological health survey by Addis Ababa University or Tikur Anbessa Hospital) was a grueling, manual process:

  • Paper Questionnaires: Researchers printed thousands of paper sheets, hired field workers to travel to rural woredas, and manually typed answers into spreadsheets weeks later. This resulted in lost forms, transcription typos, and high costs.
  • Survey Fraud & Duplicate Answers: Online survey links (like Google Forms) had no way to verify identity. One person could submit 50 fake responses to collect gift cards or skew research outcomes.
  • Payment Friction: Handing physical paper currency to hundreds of survey respondents across Ethiopia is risky and slow. Many rural participants lacked traditional bank accounts.
  • Scattered Team Coordination: Research protocols, ethical clearance certificates, raw datasets, and team communications were scattered across WhatsApp, Telegram, personal email accounts, and thumb drives.

Tinat solves all four problems in one unified platform: It verifies participant identities against Ethiopia's Fayda National Digital ID system, provides real-time digital questionnaires on computers and smartphones, pays participants instantly in Ethiopian Birr (ETB) via Telebirr or Commercial Bank of Ethiopia (CBE), and gives research teams a secure collaborative workspace with file sharing, real-time chat, and AI assistance.

1.2 Core Building Blocks Explained Simply

Concept 1

The "Frontend" (The Face of the App)

Analogy: The dining room and menu of a restaurant.

The Frontend is everything you see on your computer screen or phone when you visit Tinat. It includes buttons, input boxes, color themes, navigation menus, and animations. When a button turns green when you hover over it or a popup shows your wallet balance, that is the frontend at work.

In Tinat: Built using Next.js 14, React, and Tailwind CSS.

Concept 2

The "Backend" (The Invisible Brain)

Analogy: The kitchen and chefs behind the swinging doors.

The Backend is the server computer running in the cloud that you never see. It processes calculations, verifies whether passwords are correct, confirms whether you have enough funds in your wallet, and enforces security rules. The frontend cannot be trusted to do math because clever users could modify client code; the backend makes all authoritative decisions.

In Tinat: Built using Next.js Server Handlers running on Node.js.

Concept 3

The "Database" (The Permanent Digital Vault)

Analogy: A giant, indestructible filing cabinet with organized folders.

If the server shuts down or restarts, all memory in the computer is cleared. The Database is where information is written to permanent storage so it lasts forever. Every user account, study question, survey answer, and financial transaction is recorded in a specific "Table" (like a spreadsheet sheet) with rows and columns.

In Tinat: Built using an enterprise-grade relational database called PostgreSQL.

Concept 4

The "ORM" / Prisma (The Universal Translator)

Analogy: A professional translator who speaks both human programming code and database SQL language.

Databases speak a specialized language called SQL (Structured Query Language). Writing raw SQL can be difficult and prone to dangerous mistakes. Tinat uses Prisma ORM. Prisma lets our backend engineers write clean TypeScript code (e.g., prisma.user.findUnique(...)) and automatically translates it into fast, safe SQL commands.

In Tinat: Prisma ORM governs all 45 models in our system.

Concept 5

The "API" & "Routes" (The Digital Postal Service)

Analogy: The waiter carrying orders from dining tables to the kitchen and bringing food back.

API stands for Application Programming Interface. It is a set of secure digital addresses (called Endpoints or Routes). When you click "Submit Survey" in your browser, your browser packages your answers into a small envelope of text called a Request, sends it across the internet to an address like /api/f/[id]/submit, and waits for a Response (e.g., "Success! 50 ETB added to wallet").

Concept 6

HTTP Verbs (The Action Instructions)

Every API request tells the backend what kind of action is requested:

  • GET: "Please read and give me this data" (e.g., fetch study questions).
  • POST: "Please create something new" (e.g., submit a new answer, register an account).
  • PATCH: "Please update a specific part of an existing record" (e.g., update user bio).
  • DELETE: "Please remove this item" (e.g., delete a project file).
Concept 7

Authentication & JWT (Your Digital Passport)

Analogy: A cryptographically signed wristband given at a concert entrance.

When you log in with your email and password, the backend verifies your credentials. But how does the server remember who you are when you click to the next page? It issues an encrypted digital badge called a JWT (JSON Web Token). This token is stored securely in your browser's cookie jar. With every subsequent click, your browser automatically flashes this badge, proving who you are without asking for your password again.

Concept 8

Fayda National ID (Fraud Elimination)

Analogy: A government passport verification checkpoint.

Ethiopia's Fayda is the national digital identity system. In Tinat, users can link their Fayda ID. The system checks their national registration to confirm they are a real, living human being with a verified national identity. This guarantees that survey respondents cannot create fake duplicate accounts to collect money or distort medical statistics.

Concept 9

Financial Rails: Chapa, Telebirr & CBE

Analogy: Digital banks that convert internet clicks into real Ethiopian Birr (ETB).

When a researcher needs to fund a study (e.g., depositing 10,000 ETB for 200 participant incentives), they pay using Chapa, Ethiopia's payment gateway. When participants earn credits, they can withdraw their earnings directly to their Telebirr mobile wallet or their Commercial Bank of Ethiopia (CBE) savings account with a single click.

Concept 10

Expo & Mobile Admin App

Analogy: A portable command center in the palm of your hand.

In addition to the web platform, Tinat includes a mobile smartphone app built with React Native and Expo SDK ~58.0.19. System administrators can carry it on their Android or iOS phones to approve research studies, verify user identities, review withdrawal requests, and monitor platform health on the go.

2. The Complete Platform Journey: From Visitor to Logout

The General Map
This chapter tracks every single step of a user's experience on the Tinat platform. We show you what the user sees, what happens when they click buttons, and what the server and database are doing behind the scenes at every stage.
Figure 2.1 — Global System Navigation & State Progression Map

2.1 Phase 1: Visitor Arrival & Public Exploration

When any person opens their web browser and navigates to https://tinat.org/:

  1. The Landing Page (/):
    • Displays the platform's hero section, explaining that Tinat is Ethiopia's verified research and public health digital network.
    • Presents live platform statistics (e.g., total studies completed, verified participants, active universities).
    • Shows two primary action buttons: "Join as Researcher" and "Participate & Earn".
  2. Public Study Catalog (/studies):
    • Anyone can browse active, publicly listed research studies without logging in.
    • Each study card displays its category (e.g., Epidemiology, Maternal Health, Nutrition), estimated completion time (e.g., "7 minutes"), and the credit reward paid upon completion (e.g., "50 ETB").
  3. Public Knowledge & Policy:
    • Visitors can view /terms (Terms of Service) and /privacy (Data Privacy and Institutional Review Board compliance).

2.2 Phase 2: Registration, Email Verification & Fayda National ID

When a visitor decides to create an account, they click "Sign Up", which opens the registration screen at /register:

  1. Form Submission:
    • The user inputs their Full Name, Email Address, Phone Number, Password, and selects their desired role (Researcher or Participant).
    • When they click "Create Account", the browser makes a POST request to /api/auth/register.
    • The backend hashes the password using bcrypt (never storing plain text passwords) and saves a new record in the User database table with emailVerified: null.
  2. Email Verification (/verify-email):
    • A secure email containing a unique cryptographic verification link is dispatched.
    • When the user clicks the link, the backend hits /api/auth/verify-email, updates emailVerified = NOW(), and activates the account.
  3. The Fayda National ID Gateway (/api/auth/fayda-verify):
    • To guarantee that respondents are real Ethiopian citizens and prevent multiple fraudulent submissions, users enter their Fayda National Identification Number (FIN).
    • The backend interfaces with the national identity verification service, matches the biometric/demographic record, and marks the user's account with a verified badge.

2.3 Phase 3: Login & Role-Based Dispatching

  1. Authentication (/login):
    • The user provides their email and password.
    • The backend validates the credentials, generates an encrypted JWT session token, and stores it in an HTTP-only secure cookie.
  2. The Smart Traffic Cop (/dashboard):
    • Upon successful login, all users are automatically navigated to /dashboard.
    • The /dashboard page reads the user's role from their session token and immediately dispatches them to their dedicated workspace:
      • ADMIN: Dispatched immediately to /admin.
      • RESEARCHER: Dispatched to /researcher.
      • PARTICIPANT: Dispatched to /participant.
      • DATA COLLECTOR: Dispatched to /collector/dashboard.

2.4 Phase 4: The Researcher Journey

A researcher (such as a university professor, clinical investigator, or NGO health director) enters the Researcher Hub (/researcher):

Step 1 Designing the Study
The researcher clicks "Create New Study" (/researcher/studies/new). They enter the study title, background hypothesis, ethics clearance IRB registration number, target sample size (e.g., 500 respondents), and reward per response (e.g., 60 ETB).
Step 2 Building the Questionnaire
In the question builder, the researcher adds sections and questions: Single Select, Multiple Select, Short Text, Numerical values, Rating Scales (1 to 5), or Matrix Likert scales. Each question can be marked optional or mandatory.
Step 3 Funding the Study via Chapa
To activate the study, the researcher funds the participant reward pool. The backend calculates total incentives (500 respondents × 60 ETB = 30,000 ETB) and initiates a Chapa Payment checkout. Once paid, the study status changes from DRAFT to ACTIVE.
Step 4 Sharing Links & Social Decks
The researcher uses the "Share Study Link" button to copy the direct URL or download a QR code. They can also open the Social Deck Generator to create publication-grade image banners with customized color palettes, aspect ratios (1:1, 16:9, 9:16), and saved preset configurations for Telegram and social channels.

2.5 Phase 5: The Participant Journey (Surveys & Platform Credit Rewards)

A participant logs in to the Participant Portal (/participant):

Step 1 Discovering Eligible Studies
The participant sees a curated feed of studies they are eligible for. The card shows the research topic, institution, time commitment, and exact ETB reward.
Step 2 Answering Questions (/f/[id])
The participant reads the ethical informed consent statement and clicks "I Agree". They navigate through questions smoothly. Client-side validation ensures required questions are answered before moving forward.
Step 3 Instant Reward & Wallet Credit
Upon clicking "Submit", the backend verifies that the participant hasn't already submitted this study. It creates an append-only Response and Answer record, and instantly transfers credits to the participant's digital Wallet via an audited TinatCreditTransaction.
Step 4 Earning and Managing Non-Cash Tinat Credits
The participant navigates to /participant/wallet/withdraw. They select either Telebirr (mobile money) or Commercial Bank of Ethiopia (CBE), enter their account or phone number, and submit. The funds are disbursed directly to their real-world account.

2.6 Phase 6: Field Data Collectors (Offline & Community Enumeration)

In many rural Ethiopian woredas, community members do not have smartphones or internet access. Tinat provides the Collector Engine (/collector/dashboard):

  • Researchers invite certified field data collectors (nurses, community health workers) via CollectorInvitation.
  • The collector logs in and opens /collector/studies/[id]/collect on an Android tablet or phone.
  • The collector conducts in-person clinical interviews with rural patients, entering responses into the app.
  • Responses are saved under a CollectionSession, storing GPS verification and enumerator signatures.

2.7 Phase 7: Collaborative Research Projects & Workspace Hub

Scientific research is rarely conducted alone. The Projects Engine (/projects) provides an institutional collaboration suite:

  • Team Hierarchy: Investigators can create projects (/projects/new) and invite colleagues with distinct roles: OWNER, LEAD, MEMBER, or OBSERVER.
  • Document & File Repository: Team members upload research proposals, IRB ethical clearance certificates, raw data, and statistical scripts. Users with proper permissions can download files or permanently Delete Files when outdated or erroneous, complete with full audit logging.
  • Live Team Chat: Research teams communicate directly inside the project workspace using a dedicated chat window equipped with a full typing bar, message composer, and conversation history.
  • Task & Milestone Tracking: Projects track institutional deliverables, ethics approval dates, publication deadlines, and formal team decisions.

2.8 Phase 8: Super Administration & Mobile Management

System administrators have complete oversight through both web (/admin) and mobile (apps/admin-mobile):

  • User Governance (/admin/users): Approving researcher credentials, reviewing Fayda identification submissions, and adjusting roles.
  • Study Approvals (/admin/studies): Reviewing newly submitted studies to ensure they meet ethical and scientific standards before going live.
  • Financial Treasury & Withdrawal Processing (/admin/withdrawals): Auditing Telebirr and CBE payout batches, approving disbursements, and maintaining ledger balance.
  • Security Audit Trails (/admin/logs): Inspecting timestamped records of every sensitive operation performed on the platform.
  • Mobile Admin App: Native smartphone app built with Expo SDK ~58.0.19, allowing admins to approve withdrawals, review flagged accounts, and monitor system metrics remotely.

2.9 Phase 9: Secure Session Logout & Teardown

When a user finishes their session and clicks "Sign Out":

  1. The browser initiates a POST request to /api/auth/logout.
  2. The backend clears the HTTP-only JWT session cookie from the browser and destroys any active server session caches.
  3. An ActivityLog entry is written to record the logout event with timestamp and IP address.
  4. The browser purges local in-memory states (TanStack React Query caches) and redirects the user safely back to the public landing page (/).

A database model is like a master template for a specific spreadsheet table. Every time an action happens on Tinat (such as someone creating an account, asking a question, or recording a research answer), a new row is permanently recorded in one of these 59 tables. 3.2 All 59 Database Models Explained in Detail

Below is the complete inventory of all 59 database models in Tinat, organized into logical business functional clusters.

Cluster 1: User Identity, Authentication & Security

Model 1 User — The Core Identity Vault

What it represents: Every single human or administrative account on the platform.

Key Fields: id (Unique ID), name, email (Login username), passwordHash (Encrypted bcrypt password), role (RESEARCHER, PARTICIPANT, ADMIN), faydaId (Linked Ethiopian National ID), isVerified, emailVerified, createdAt.

Relationships: Connects to Wallet (1:1), Study (created studies), Response (surveys answered), ProjectMember (projects joined), Verification (proofs submitted).

Model 2 Verification — National ID & Academic Verification

What it represents: Records of Fayda National ID checks and university faculty credentials.

Key Fields: id, userId, type (FAYDA_NATIONAL_ID, ACADEMIC_CREDENTIAL), idNumber, documentUrl, status (PENDING, APPROVED, REJECTED), reviewedBy, reviewedAt.

Purpose: Guarantees that users are real Ethiopian citizens and authenticates research credentials.

Model 3 ActivityLog — System Audit Trail

What it represents: An append-only, tamper-evident security record of actions taken on the system.

Key Fields: id, userId, action (e.g. LOGIN, STUDY_CREATED, FILE_DELETED, WITHDRAWAL_APPROVED), details (JSON), ipAddress, createdAt.

Model 4 Notification — In-App User Alerts

What it represents: Real-time alerts sent to users' bell icons (e.g. "Your survey reward of 50 ETB was credited").

Key Fields: id, userId, title, message, link, read (true/false), createdAt.

Model 5 AdminChatMessage — Admin Communication Channel

What it represents: Direct internal messages between system administrators in the admin console.

Key Fields: id, senderId, recipientId, message, read, createdAt.

Cluster 2: Research Studies, Questions & Responses

Model 6 Study — The Research Investigation

What it represents: A clinical trial, health questionnaire, or public survey authored by a researcher.

Key Fields: id, creatorId, title, description, status (DRAFT, ACTIVE, COMPLETED), type (SURVEY, EPIDEMIOLOGICAL), rewardAmount (ETB paid per answer), targetSample, currentResponses, ethicalApprovalNumber (IRB clearance), bannerUrl, socialDeckConfig (custom saved dimensions and colors).

Model 7 Question — Individual Survey Questions

What it represents: A specific question within a study (e.g. "Have you experienced persistent fever?").

Key Fields: id, studyId, text, description, type (SINGLE_SELECT, MULTI_SELECT, RATING, etc.), order (display position), isRequired (true/false).

Model 8 QuestionOption — Multiple Choice Options

What it represents: Selectable answer choices for single-choice or multi-choice questions (e.g. "Yes", "No", "Unsure").

Key Fields: id, questionId, text, value, order.

Model 9 QuestionRow — Matrix & Likert Scale Items

What it represents: The sub-rows inside a matrix question (e.g. "Rate hospital cleanliness", "Rate nurse attentiveness").

Key Fields: id, questionId, text, order.

Model 10 Response — A Completed Survey Submission

What it represents: A participant's full submission for a study.

Key Fields: id, studyId, participantId, collectorId (if collected by enumerator), ipHash, deviceFingerprint, completedAt, rewardEarned.

Model 11 Answer — Individual Answer Value

What it represents: The specific answer provided to a specific question within a response.

Key Fields: id, responseId, questionId, textValue, numberValue, selectedOptionId, matrixRowId.

Model 12 StudyBookmark — Saved Studies

What it represents: A bookmark when a participant saves a study to complete later.

Key Fields: id, userId, studyId, createdAt.

Model 13 StudyRating — Participant Feedback on Studies

What it represents: 1-to-5 star ratings left by participants evaluating whether the study questions were clear and respectful.

Key Fields: id, studyId, userId, rating (1-5), feedback, createdAt.

Model 14 StudyLike — Community Endorsement

What it represents: Likes given by academic peers to highlight impactful research.

Key Fields: id, studyId, userId, createdAt.

Model 15 StudyComment — Public & Participant Discussion

What it represents: Public comments and feedback posted under research study listings.

Key Fields: id, studyId, userId, content, parentId (for threaded replies), createdAt.

Cluster 3: Financial Infrastructure, Wallets & Payouts

Model 16 Wallet — Digital Credit Account

What it represents: The balance account holding Ethiopian Birr credits for each user.

Key Fields: id, userId, balance (Current spendable or withdrawable balance in ETB), pendingBalance, totalEarned, totalWithdrawn, updatedAt.

Model 17 TinatCreditTransaction — Append-Only Financial Ledger

What it represents: Every single credit or debit entry in the system. Follows double-entry accounting principles.

Key Fields: id, walletId, amount (positive for credits, negative for debits), type (STUDY_REWARD, WITHDRAWAL, STUDY_FUNDING), description, balanceAfter, createdAt.

Model 18 StudyPayment — Chapa Study Funding Record

What it represents: Payments made by researchers to fund their study incentives through Chapa.

Key Fields: id, studyId, userId, amount, currency (ETB), chapaReference, status (PENDING, SUCCESS, FAILED), createdAt.

Model 19 Withdrawal — Telebirr & CBE Payout Requests

What it represents: A participant's formal request to transfer wallet credits to their real-world bank or mobile money account.

Key Fields: id, walletId, amount, method (TELEBIRR, CBE), accountNumber, accountName, status (PENDING, COMPLETED, REJECTED), approvedBy, processedAt.

Cluster 4: Collaborative Research Projects & Workspace Hub

Model 20 ResearchProject — Collaborative Workspace

What it represents: An overarching institutional research investigation uniting multiple scientists.

6. Specialized Platform Engine Deep-Dives

Deep Technical Inspection
This chapter dives deep into the custom-engineered systems that set Tinat apart from ordinary web tools: the Ethiopian financial rails, Fayda National ID verification, the upgraded collaborative research workspace (with file deletion and enhanced chat), the social deck generator with saved presets, and the mobile admin application.

6.1 The Credit Economy Engine: Non-Cash Tokens & Quarantined Legacy Rails

One of Tinat's most critical innovations is the ability to allocate and disburse Tinat Credits (non-cash platform tokens) transparently between institutional research budgets and participants.

Figure 6.1 — Financial Flow Lifecycle & Double-Entry Ledger

1. How Money Enters: The Chapa Gateway Integration

When a researcher creates a study for 500 respondents offering 60 ETB per survey, they must fund the participant escrow pool (30,000 ETB).

  • The backend calls Chapa's initialization API (https://api.chapa.co/v1/transaction/initialize) and receives a unique checkout URL.
  • The researcher pays using a local debit card, Telebirr, or CBE Birr.
  • Upon payment completion, Chapa calls our secure webhook at /api/auth/payments/chapa/callback.
  • The backend verifies the cryptographic webhook signature, updates StudyPayment.status = SUCCESS, and automatically flips the study status from DRAFT to ACTIVE.

2. The Double-Entry Ledger (TinatCreditTransaction)

To prevent money from vanishing or being duplicated, Tinat uses an append-only double-entry ledger. Balance is never updated in isolation; every single coin moved creates a permanent transaction record: 

// Example: Crediting a participant 50 ETB upon survey completion
await prisma.$transaction([
  prisma.wallet.update({
    where: { userId: participantId },
    data: { balance: { increment: 50.0 } }
  }),
  prisma.tinatCreditTransaction.create({
    data: {
      walletId: participantWallet.id,
      amount: 50.0,
      type: "STUDY_REWARD",
      description: "Incentive reward for completing Study #TIN-492",
      balanceAfter: participantWallet.balance + 50.0
    }
  })
]);

3. Real Payouts: Telebirr & Commercial Bank of Ethiopia (CBE)

When a participant completes studies, they earn Tinat Credits under the platform token economy:

  • Telebirr: Real-time mobile money transfer directly to the participant's Ethio Telecom mobile phone number. Ideal for students and rural citizens without bank branches.
  • Commercial Bank of Ethiopia (CBE): Direct bank deposit into the participant's CBE savings account. Preferred for larger payout amounts.
  • Admin Approval Queue: Withdrawals are protected by an administrative check in /admin/withdrawals. System administrators audit the request against fraud flags before the funds are dispatched.

6.2 The Ethiopian National ID (Fayda) Verification Pipeline

Data integrity is the cornerstone of clinical and medical research. If respondents are fake bots or one person takes a survey 20 times using different browser tabs, the statistical epidemiological conclusions are ruined.

Step 1

National ID Input & Format Validation

During registration or from their profile settings, the user provides their Fayda Identification Number (FIN). The system validates the format against the official Ethiopian Digital ID standard.

Step 2

Cryptographic Identity Verification

The backend interfaces with the Fayda verification endpoint (/api/auth/fayda-verify). The user verifies their phone or biometric OTP. Once confirmed, a Verification record is generated and the user account receives a cryptographically verified status.

Anti-Fraud Impact: Because every survey response is tied to an audited account, a single human being with one Fayda ID can only complete a study once. Reduces duplicate and fake accounts through national ID verification and additional integrity checks.

7. Production Operations, Security & Compliance

7.1 Ethical Adherence & Clinical Research Compliance (IRB / GCP)

Tinat was engineered in accordance with international Good Clinical Practice (GCP) guidelines and Ethiopian National Ethics Review Committee (NERC) protocols:

  • Informed Consent Recording: Every clinical study enforces an explicit, unskippable digital consent screen before revealing study questions. The participant's agreement timestamp and browser fingerprint are permanently attached to the response.
  • Data Anonymization: When researchers export microdata to Excel, SPSS, or CSV, personally identifiable information (Full Name, Phone Number, Fayda National ID Number) is automatically masked or excluded to protect patient confidentiality.
  • Audit Trails for Data Access: When an administrator or investigator downloads an exported dataset, an append-only ActivityLog is generated detailing who accessed the file, at what exact millisecond, and from which IP address.

7.2 Web Application Security Guardrails

The Tinat platform implements defense-in-depth protection across all layers of the application:

Protection 1

SQL Injection & ORM Shielding

Traditional SQL vulnerabilities occur when raw user input is concatenated into database queries. Tinat uses Prisma ORM, which employs strict parameterized queries and typed inputs. Raw SQL strings are prohibited.

Protection 2

Cross-Site Scripting (XSS) Prevention

All user input (questions, comments, chat messages) is sanitized and rendered through React's virtual DOM, which automatically escapes dangerous HTML tags and prevents script injection.

Protection 3

Cross-Site Request Forgery (CSRF) & Cookies

Authentication cookies use the SameSite=Lax and HttpOnly flags. Client-side JavaScript cannot read the session cookie, eliminating session hijacking via malicious browser extensions.

Protection 4

Role-Based Access Control (RBAC)

Next.js edge middleware (middleware.ts) evaluates every incoming request against the user's role. A participant attempting to access /admin or /api/admin/* is blocked at the network perimeter before server CPU cycles are expended.

Summary of Production Security Verification
The Tinat ecosystem combines government-level identity verification (Fayda), cryptographic verification (Fayda / Jose), append-only double-entry ledger bookkeeping (PostgreSQL), and modern TypeScript web architecture to establish a hardened, reliable scientific research infrastructure.
