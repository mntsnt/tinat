1. Foundations in Plain English: How Web Platforms Work

Who This Chapter Is For

If you have never written a line of code or built a website, this chapter is for you. We explain all technical terms (like "frontend", "backend", "database", "API", and "JWT") using simple real-world analogies so you can easily understand how the Tinat platform functions from top to bottom.

1.1 The Real-World Mission: What is Tinat?

Tinat (derived from the Ge'ez / Amharic root ጥናት, meaning "Rigorous Scientific Study" or "In-depth Research") is a complete digital operating system built for medical, public health, and academic research in Ethiopia.

Historically, conducting a research study in Ethiopia (such as an epidemiological health survey by Addis Ababa University or St. Paul's Hospital Millennium Medical College) was a grueling, manual process:

  • Paper Questionnaires: Researchers printed thousands of paper sheets, hired field workers to travel to rural woredas, and manually typed answers into spreadsheets weeks later. This resulted in lost forms, transcription typos, and high costs.
  • Survey Fraud & Duplicate Answers: Online survey links (like Google Forms) had no way to verify identity. One person could submit 50 fake responses to collect rewards or skew research outcomes.
  • Payment Friction: Handing physical cash to hundreds of survey respondents across Ethiopia is risky and slow. Many rural participants lacked traditional bank accounts.
  • Scattered Team Coordination: Research protocols, ethical clearance certificates, raw datasets, and team communications were scattered across WhatsApp, Telegram, personal email accounts, and thumb drives.

Tinat solves all four problems in one unified platform: It verifies participant identities against Ethiopia's Fayda National Digital ID system, provides real-time digital questionnaires on computers and smartphones, pays participants instantly in Ethiopian Birr (ETB) via Telebirr or Commercial Bank of Ethiopia (CBE), provides standalone Tinat Forms, and gives research teams a secure collaborative workspace with file sharing, real-time chat, and AI assistance.

1.2 Core Building Blocks Explained Simply

CONCEPT 1 The "Frontend" (The Face)
Analogy: The dining room and menu of a restaurant.
The Frontend is everything you see on your screen when you visit Tinat. It includes buttons, input boxes, color themes, navigation menus, and charts. When a button turns green when you hover or your balance card tilts, that is the frontend.

In Tinat: Built using Next.js 16, React, and Tailwind CSS v4.

CONCEPT 2 The "Backend" (The Brain)
Analogy: The kitchen and chefs behind swinging doors.
The Backend is the server running in the cloud that you never see. It processes calculations, verifies passwords, checks wallet balances, and enforces ethics rules. The frontend cannot be trusted to do math; the backend makes all authoritative decisions.

In Tinat: Next.js Server Handlers & Server Actions on Node.js.

CONCEPT 3 The "Database" (The Vault)
Analogy: A giant indestructible filing cabinet.
If the server shuts down or restarts, all RAM is cleared. The Database is where information is written permanently. Every user account, study question, survey answer, and financial ledger row is stored in a specific table with columns.

In Tinat: Enterprise-grade PostgreSQL 16 relational database.

CONCEPT 4 The "ORM" / Prisma (Translator)
Analogy: A professional translator speaking code and SQL.
Databases speak SQL (Structured Query Language). Writing raw SQL can be difficult and prone to dangerous injection mistakes. Tinat uses Prisma ORM to let engineers write clean TypeScript code that automatically converts into fast, safe SQL queries.

In Tinat: Prisma ORM v7 governs all 45 models in our system.

CONCEPT 5 The "API" (The Postal Service)
Analogy: Waiter carrying orders to kitchen and back.
API stands for Application Programming Interface. It is a set of secure digital addresses (Routes). When you click "Submit Survey", your browser packages your answers into a Request envelope, sends it across the web to an address, and waits for a Response.

In Tinat: 85 REST API Endpoints governing data flow.

CONCEPT 6 HTTP Verbs (Action Verbs)
Every request tells the backend what action is requested:
• GET: "Please read and return this data" (e.g. fetch questions).
• POST: "Please create something new" (e.g. submit response).
• PATCH: "Please update a specific field" (e.g. edit user bio).
• DELETE: "Please remove this item" (e.g. delete a draft file).

Standardized RESTful HTTP protocols throughout.

1.2 Core Building Blocks (Continued)

CONCEPT 7 Authentication & JWT (Wristband)
Analogy: A tamper-proof wristband given at a concert entrance.
When you log in with your email and password, the backend verifies your credentials. How does the server remember who you are on the next page? It issues an encrypted digital badge called a JWT (JSON Web Token) stored in your cookie jar. Every click flashes this badge automatically.

In Tinat: Cryptographic HMAC-SHA256 JWT tokens using jose.

CONCEPT 8 Fayda National ID (Biometric Gate)
Analogy: A government passport verification checkpoint.
Ethiopia's Fayda is the national digital identity system. In Tinat, users link their Fayda ID. The system checks their national registration to confirm they are a real, living citizen. This guarantees that survey respondents cannot create fake duplicate accounts to manipulate medical data.

In Tinat: SHA-256 FAN Hashing with strict de-identification.

CONCEPT 9 Financial Rails: Telebirr & CBE
Analogy: Digital channels converting clicks into Ethiopian Birr.
When a researcher funds a study, they deposit via Chapa payment gateway. When participants earn credits, they can withdraw their earnings directly to their Telebirr mobile wallet or Commercial Bank of Ethiopia (CBE) savings account with a single click.

In Tinat: Double-entry append-only immutable ledger accounting.

CONCEPT 10 Tinat Forms (No-Code Builder)
Analogy: An instant, lightweight localized Google Forms.
For independent academic student research or campus feedback that does not require formal multi-month hospital IRB clearance, Tinat Forms provides a visual drag-and-drop builder with short shareable links (/f/[id]) and direct Excel downloads.

In Tinat: Standalone survey engine streaming .xlsx workbooks.

CONCEPT 11 Field Enumerators (Offline Census)
Analogy: Digital clipboard working in remote mountains.
In rural Ethiopian kebeles without mobile reception, 4th-year medical students conduct household interviews offline. The app stores answers locally in the device's IndexedDB and automatically synchronizes to the cloud the moment cell coverage is re-established.

In Tinat: Offline-first IndexedDB cache with batch upload API.

CONCEPT 12 Expo & Mobile Admin App
Analogy: A portable command center in the palm of your hand.
In addition to the web platform, Tinat includes a smartphone app built with React Native and Expo SDK 54. System administrators can carry it on their Android or iOS phones to approve research studies, verify user identities, and monitor platform health on the go.

In Tinat: React Native 0.88 + Expo SDK 54 mobile application.

1. Foundations: Platform Architecture & Technology Stack

1.3 Technology Stack: Why Tinat Runs on PERN (and Not MERN)

Definitive Architectural Classification: PERN vs. MERN

A foundational question for technical evaluators is whether Tinat uses MERN (MongoDB, Express, React, Node.js) or PERN (PostgreSQL, Express / Next.js Server Handlers, React, Node.js). The Tinat Research Ecosystem is strictly and exclusively built on the PERN stack. MongoDB is not present anywhere in the codebase. Every single data model, survey response, and financial transaction is governed by PostgreSQL 16 through Prisma ORM v7 with the @prisma/adapter-pg connection pool.

Figure 1.1 — Tinat PERN Architecture & Multi-Tier Runtime Pipeline

Technical Breakdown: Why PostgreSQL (PERN) Over MongoDB (MERN)

Architectural Dimension Tinat Implementation (PERN — PostgreSQL 16) Legacy Alternative (MERN — MongoDB)
Financial Escrow Ledgers Strict ACID Atomicity: All credit movements (Chapa deposits, participant rewards, platform fee splits, Telebirr cashouts) execute inside atomic prisma.$transaction blocks. Balances and transaction logs commit simultaneously or rollback entirely. Eventual Consistency Risks: Document-level locking and eventual consistency in distributed clusters can introduce race conditions and double-spending vulnerabilities during concurrent high-volume survey payouts.
Survey Relational Logic Relational Cascades: Workspaces → Projects → Studies → Sections → Questions → Conditional Branches → Responses are joined with strict referential integrity. Deleting a study safely cascades or archives related questions. Document Size Limits & Orphans: Storing thousands of participant responses inside nested study documents quickly violates MongoDB's 16 MB BSON document limit; referencing across collections lacks enforced foreign-key constraints.
Identity & Sybil Prevention Database-Level Unique Constraints: National identity hashes (faydaFanHash) and email addresses are enforced by B-tree unique indexes at the database engine level, guaranteeing that no bot or duplicate account can slip through. Application-Level Index Reliance: In sharded or replica sets, unique index constraints can occasionally allow duplicate writes under severe network partitions or high concurrent insertion bursts.
Audit Immutability PL/pgSQL Append-Only Triggers: Low-level database triggers intercept any attempted UPDATE or DELETE statements on settled rows in FinancialTransaction, guaranteeing compliance with national financial audit standards. Code-Dependent Immutability: Document databases cannot easily enforce table-level immutability triggers at the database engine level, leaving ledgers vulnerable if application middleware is bypassed.
Unstructured Flexibility PostgreSQL Native JSONB: Combines relational rigor for users and wallets with high-performance binary JSON (JSONB) columns for dynamic survey question options and branching condition rules. Schema Drift: Unstructured JSON collections frequently accumulate schema drift across software releases, requiring fragile manual data migration scripts.

2. The Complete Platform Journey: From Visitor to Logout

The General Map

This chapter tracks every single step of a user's experience on the Tinat platform. We show you what the user sees, what happens when they click buttons, and what the server and database are doing behind the scenes at every stage.

Figure 2.1 — Global System Navigation & State Progression Map

2.1 Phase 1: Visitor Arrival & Public Exploration

When any person opens their web browser and navigates to https://tinat.et/:

  • The Landing Page ( / ): Displays the platform's hero section, explaining that Tinat is Ethiopia's verified research and public health digital network. Presents live platform statistics (completed surveys, verified participants, active universities) and call-to-actions ("Join as Researcher" and "Participate & Earn").
  • Public Study Catalog ( /studies ): Anyone can browse active, publicly listed research studies without logging in. Each study card displays its category (e.g. Epidemiology, Maternal Health, Nutrition), estimated completion time ("7 minutes"), and credit reward ("25 TC").
  • Public Policy Pages: Visitors can inspect /terms (Terms of Service) and /privacy (Data Protection proclamation adherence and IRB guidelines).

2.2 Phase 2: Registration, Email Verification & Fayda National ID

When a visitor clicks "Sign Up", which opens the registration screen at /register:

  • Form Submission: The user inputs Full Name, Email Address, Phone Number, Password, and selects their desired role (Researcher or Participant). Clicking "Create Account" triggers a POST /api/auth/register request, hashing the password via bcrypt (salt 10) and initializing an unverified User record.
  • Email Verification ( /verify-email ): A secure email with a cryptographic token is dispatched. Clicking the link hits /api/auth/verify-email and sets isVerified = true.
  • Fayda National ID Gateway ( /api/auth/fayda-verify ): To ensure respondents are real citizens and block duplicate accounts, users verify their Fayda Identification Number (FIN). The backend validates the SHA-256 hash against User.faydaFanHash.

2.3 Phase 3: Login & Role-Based Dispatching

  • Authentication ( /login ): The user provides email and password. The backend checks credentials, signs an encrypted JWT session token via jose, and stores it in an HTTP-only secure cookie.
  • The Smart Traffic Cop ( /dashboard ): When navigating to /dashboard, the page reads the user's role from their active session token and dispatches them automatically: ADMIN ➔ /admin | RESEARCHER ➔ /researcher | PARTICIPANT ➔ /participant | DATA_COLLECTOR ➔ /collector/dashboard.

2.4 Phase 4: The Researcher Journey

A researcher (such as a university professor, clinical investigator, or public health director) enters /researcher:

STEP 1Designing the Study
Clicks "Create New Study" (/researcher/studies/new). Inputs study title, hypothesis, target sample size (e.g. 500 respondents), ethics clearance IRB number, and reward per participant (e.g. 25 TC).
STEP 2Building the Questionnaire
Adds sections and questions: Single Select, Multiple Select, Short/Long Text, Numerical values, Rating Scales (1 to 5), or Matrix Likert tables. Configures optional or mandatory validation flags.
STEP 3Funding the Study via Chapa
To activate, the researcher funds the participant reward pool (e.g. 500 × 25 TC). The backend calculates the total, initiates a Chapa checkout, and upon webhook confirmation transitions study status from DRAFT to ACTIVE.
STEP 4Sharing Links & Social Decks
Uses "Share Study Link" to copy direct URL or generate QR codes. Opens the Social Deck Generator to download branded promotion cards formatted for Telegram channels, LinkedIn, and Facebook.

2.5 Phase 5: The Participant Journey (Surveys & Real Payouts)

A participant logs in to the Participant Portal ( /participant ):

STEP 1Discovering Eligible Studies
The participant sees a curated feed of studies they qualify for. The card shows the research topic, medical institution, time commitment, and exact ETB reward.
STEP 2Answering Questions ( /f/[id] )
Reads the ethical informed consent statement and clicks "I Agree". Navigates questions smoothly with client-side validation ensuring required fields are completed.
STEP 3Instant Reward & Wallet Credit
Upon clicking "Submit", the backend verifies anti-fraud and single-submission limits, creates an immutable Response and Answer row, and credits the digital Wallet via an audited transaction.
STEP 4Cashout via Telebirr or CBE
Navigates to /participant/wallet/withdraw. Selects Telebirr or Commercial Bank of Ethiopia (CBE), enters phone or account number, and submits request for automated or audited dispatch.

2.6 Phase 6: Field Data Collectors (Offline & Community Enumeration)

In rural woredas without cellular connectivity, Tinat provides the Collector Engine ( /collector/dashboard ):

  • Researchers invite certified medical student enumerators via CollectorInvitation.
  • The collector opens /collector/studies/[id]/collect on an Android tablet or smartphone.
  • Conducts in-person clinical interviews with rural households; responses cache inside IndexedDB with GPS coordinates.
  • When internet restores, batch sync dispatches to /api/collector/sessions/sync with automated conflict resolution.

2.7 Phase 7: Collaborative Research Projects & Workspace Hub

The Projects Engine ( /projects ) provides an institutional collaboration suite:

  • Team Hierarchy: Investigators create projects (/projects/new) and invite colleagues with roles: OWNER, LEAD, MEMBER, or OBSERVER.
  • Document & File Repository: Team members upload proposals, IRB clearance certificates, datasets, and scripts. Authorized leads can permanently Delete Files with full audit logging.
  • Live Team Chat: Research teams communicate directly using a dedicated chat window with typing bars, avatars, and message history.
  • Task & Milestone Tracking: Kanban boards track ethics review dates, publication deadlines, and formal team decisions.

2.8 Phase 8: Super Administration & Mobile Management

System administrators possess complete oversight through web ( /admin ) and mobile ( apps/admin-mobile ):

  • User Governance ( /admin/users ): Approving researcher credentials, reviewing Fayda submissions, filtering by roles, and account moderation.
  • Study Approvals ( /admin/studies ): Reviewing newly submitted research proposals to ensure ethical clearance before going live.
  • Geographic Reach ( /admin/geographic ): Zero-scroll fixed map monitoring enumerator density across all 12 regional states.
  • Financial Treasury ( /admin/withdrawals ): Auditing Telebirr and CBE payout batches and approving disbursements.

2.9 Phase 9: Secure Session Logout & Teardown

When a user finishes their session and clicks "Sign Out":

  1. The browser initiates a POST /api/auth/logout request.
  2. The backend clears the HTTP-only JWT session cookie from the browser and invalidates active server session caches.
  3. An ActivityLog entry is permanently recorded with the logout event timestamp and IP address.
  4. The browser purges local in-memory states (TanStack React Query caches) and redirects safely back to the public landing page ( / ).

Below is the complete inventory of all 45 database models in Tinat, organized into logical business functional clusters:

Cluster 1: User Identity, Authentication & Security

MODEL 1User — The Core Identity Vault
What it represents: Every single human or administrative account on the platform.

6.1 The Financial Engine: Chapa, Wallets & Telebirr / CBE Payouts

One of Tinat's most critical innovations is the ability to move real money (Ethiopian Birr - ETB) seamlessly between institutional research budgets and individual citizens.

Figure 6.1 — Financial Flow Lifecycle & Double-Entry Ledger

1. How Money Enters: The Chapa Gateway Integration

When a researcher creates a study for 500 respondents offering 25 ETB per survey, they must fund the participant escrow pool (12,500 ETB):

  • The backend calls Chapa's initialization API (https://api.chapa.co/v1/transaction/initialize) and receives a unique checkout URL.
  • The researcher pays using a local debit card, Telebirr, or CBE Birr.
  • Upon payment completion, Chapa calls our secure webhook at /api/auth/payments/chapa/callback.
  • The backend verifies the cryptographic webhook signature, updates StudyPayment.status = SUCCESS, and automatically flips the study status from DRAFT to ACTIVE.

2. The Double-Entry Ledger (TinatCreditTransaction)

To prevent money from vanishing or being duplicated, Tinat uses an immutable ledger. Balance is never updated in isolation; every single coin moved creates a permanent transaction record:

// Example: Crediting a participant 25 ETB upon survey completion inside an atomic transaction
await prisma.$transaction([
  prisma.wallet.update({
    where: { userId: participantId },
    data: { balance: { increment: 25.0 } }
  }),
  prisma.tinatCreditTransaction.create({
    data: {
      walletId: participantWallet.id,
      amount: 25.0,
      type: "STUDY_REWARD",
      description: "Incentive reward for completing Study #TIN-492",
      balanceAfter: participantWallet.balance + 25.0
    }
  })
]);

3. Real Payouts: Telebirr & Commercial Bank of Ethiopia (CBE)

When a participant accumulates earnings, they can cash out through two national payment channels:

  • Telebirr: Real-time mobile money transfer directly to the participant's Ethio Telecom mobile phone number. Ideal for students and rural citizens without bank branches.
  • Commercial Bank of Ethiopia (CBE): Direct bank deposit into the participant's CBE savings account. Preferred for larger payout amounts.
  • Admin Approval Queue: Withdrawals are protected by an administrative check in /admin/withdrawals. System administrators audit the request against fraud flags before funds are dispatched.

6.2 The Ethiopian National ID (Fayda) Verification Pipeline

Data integrity is the cornerstone of clinical and medical research. If respondents are fake bots or one person takes a survey 20 times using different browser tabs, statistical epidemiological conclusions are ruined.

Figure 6.2 — Fayda National ID Cryptographic Verification & FAN Hashing Pipeline
STEP 1National ID Input & Validation
During registration or from profile settings, the user provides their Fayda Identification Number (FIN). The system validates the format against the official Ethiopian Digital ID standard.
STEP 2Cryptographic Identity Verification
The backend interfaces with the Fayda verification endpoint (/api/auth/fayda-verify). The user verifies their phone OTP. Once confirmed, a Verification record is generated and account verified.

Anti-Fraud Impact

Because every survey response is tied to an audited account, a single human being with one Fayda ID can only complete a study once. Duplicate bot submissions are structurally impossible.

7. Production Operations, Security & Compliance

7.1 Ethical Adherence & Clinical Research Compliance (IRB / GCP)

Tinat was engineered in accordance with international Good Clinical Practice (GCP) guidelines and Ethiopian National Ethics Review Committee (NERC) protocols:

  • Informed Consent Recording: Every clinical study enforces an explicit, unskippable digital consent screen before revealing study questions. The participant's agreement timestamp and browser fingerprint are permanently attached to the response.
  • Data Anonymization: When researchers export microdata to Excel, SPSS, or CSV, personally identifiable information (Full Name, Phone Number, Fayda National ID Number) is automatically masked or excluded to protect patient confidentiality.
  • Audit Trails for Data Access: When an administrator or investigator downloads an exported dataset, an immutable ActivityLog is generated detailing who accessed the file, at what exact millisecond, and from which IP address.

7.2 Web Application Security Guardrails

The Tinat platform implements defense-in-depth protection across all layers of the application:

PROTECTION 1SQL Injection & ORM Shielding
Traditional SQL vulnerabilities occur when raw user input is concatenated into database queries. Tinat uses Prisma ORM, which employs strict parameterized queries and typed inputs. Raw SQL strings are prohibited.
PROTECTION 2Cross-Site Scripting (XSS) Prevention
All user input (questions, comments, chat messages) is sanitized and rendered through React's virtual DOM, which automatically escapes dangerous HTML tags and prevents script injection.
PROTECTION 3CSRF & Cookie Protection
Authentication cookies use the SameSite=Lax and HttpOnly flags. Client-side JavaScript cannot read the session cookie, eliminating session hijacking via malicious browser extensions.
PROTECTION 4Role-Based Access Control (RBAC)
Next.js edge middleware (middleware.ts) evaluates every incoming request against the user's role. A participant attempting to access /admin or /api/admin/* is blocked at the network perimeter before server CPU cycles are expended.

Summary of Production Security Verification

The Tinat ecosystem combines government-level identity verification (Fayda), banking-grade payment encryption (Chapa), immutable double-entry ledger bookkeeping (PostgreSQL), and modern TypeScript web architecture to establish the most secure and reliable scientific research infrastructure in East Africa.
